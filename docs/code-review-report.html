🏗️ 一、架构问题

1. 数据库双写不同步 — SQLite 与 MySQL 字段不一致

🔴 高风险

app/db/store.py + app/db/mysql_schema.py

Supplier 表在 SQLite 中已扩展（本次会话修复），但 Product、PurchaseInRecord、SettlementRecord 等其他表同样存在 SQLite 定义少于 MySQL 或 Repository 实际使用的字段。MySQL 启用时会因字段缺失直接报错。

建议：编写一个 _verify_schema_sync() 函数，启动时对 SQLite/MySQL 进行 PRAGMA table_info 对比校验。

2. 响应格式不统一

🟡 中风险

backend/api/routes/agreement_price.py, storage.py 等

项目约定响应格式为 {success, message, items, total}，但部分路由直接返回 {"success": True, "message": "xxx"} 或裸 {"ok": true}。 agreement_price.py 直接操作数据库而不经过 Service 层。

3. 部分模块缺少 Service 层

🟡 中风险

backend/api/routes/agreement_price.py, storage.py

agreement_price 和 storage 路由直接在 Route 层调用 simple_update/simple_delete， 跳过了 Service 层。这导致业务逻辑散落在 Route 中，无法复用、无法单测。

🔒 二、安全问题

4. 自动生成的残留文件在仓库中

🔴 高风险

config/mcporter.json, _tok.txt, =7.0.0, mcp_commands.txt

这些文件包含了本地环境配置和 token 信息。虽然 .gitignore 已更新但之前已提交的版本 仍残留在 Git 历史中。建议用 git filter-repo 清理历史。

5. 前端 API 错误处理不完整

🟡 中风险

frontend/src/views/*.vue (多处)

多个 Vue 组件中的 API 调用用 try {} catch {} 静默吞掉错误。 用户看不到后端返回的具体错误信息。例如 OrderManagement.vue 的 handleDelete 在 catch 中仅 // 用户取消或报错。 

// 当前
} catch {
  // 用户取消或报错
}

// 建议
} catch (e: any) {
  if (e !== 'cancel') {
    ElMessage.error(e?.response?.data?.detail || '操作失败')
  }
}

6. Token 存放在 localStorage

🔵 建议

frontend/src/api/client.ts

JWT token 存储在 localStorage 中，易受 XSS 攻击。对于内部系统可接受， 但建议后续迁移到 httpOnly cookie 或使用 fingerprint + session 方案。

📋 三、代码质量问题

7. 裸 except 子句

🟡 中风险

app/db/migration.py, app/views/data_transfer_view.py, app/views/main_window.py

三个文件使用了裸 except:，会捕获 KeyboardInterrupt 和 SystemExit，导致程序无法正常终止。 

# 坏
try:
    do_something()
except:
    pass

# 好
try:
    do_something()
except Exception as e:
    logger.error("操作失败: %s", e)

8. 超大文件需要拆分

🔵 建议

frontend/src/views/OrderManagement.vue (917 行), app/db/store.py (1998 行)

OrderManagement.vue 集列表/筛选/新建/编辑/复制/删除/日期筛选/商户搜索/商品搜索于一体， 即将突破 1000 行。建议拆分为 composables： useOrderList / useOrderForm / useMerchantSearch。

9. 缺少请求日志/审计追踪

🔵 建议

backend/api/routes/*.py

当前只有认证相关的审计日志。CRUD 操作（如创建/删除订单、修改供应商）没有记录操作人和操作时间。 建议在关键写操作中加入 AuditLog 记录。

🐛 四、潜在 Bug

10. 订单交易概况查询可能匹配错误供应商

🔴 高风险

backend/services/supplier_service.py:get_transaction_summary()

交易概况用 oi.product_name LIKE '%供应商名%' 关联订单，如果 供应商名是常见词（如"测试"），会错误匹配其他供应商的商品。

建议：改成通过 OrderRecord.merchant_name 精确匹配，或通过关联表查询。

11. SQLite UPDATE 的通用写法可能 SQL 注入

🟡 中风险

app/db/supplier_repository.py:update()

update() 方法动态拼接字段名：f"{key} = ?"。 如果 data 中的 key 来自不可信输入（虽然当前来自 Pydantic）， 存在潜在风险。建议对字段名做白名单校验。

12. 前端路由缺少 404 兜底

🔵 建议

frontend/src/navigation/appNavigation.ts

没有定义 catch-all 路由（path: '/:pathMatch(.*)*'），访问不存在的页面会白屏。
